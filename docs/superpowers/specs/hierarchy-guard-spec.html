Hierarchy Guard

Shows the parent and child structure of pages inside wp-admin, warns before a slug change, re-parenting, or trash breaks a subtree, and makes sure every old URL has somewhere to go.

Why this exists

WordPress protects posts from broken URLs. It does nothing for pages.

Pages and every hierarchical custom post type build their URLs from the chain of ancestors. Change one link in that chain and every URL below it changes too. Core knows how to redirect an old slug for a post, but both halves of that mechanism explicitly skip hierarchical types. The behaviour below was verified by reading WordPress 6.8.1 source.

Editor actionWhat core doesWhat visitors get
Rename a page's slugNothing stored. wp_check_for_changed_slugs() returns early for hierarchical types, and wp_old_slug_redirect() returns early as well.404 on the page's old URL and on every subpage's old URL
Move a page under a different parentNothing stored, same two early returns.404 across the whole moved subtree
Trash a parentThe parent's slug is renamed to about__trashed on the spot. Subpages are left attached to it. No warning.404 on /about/team/ while the subpage stays live at /about__trashed/team/
Delete a parent permanentlySubpages are re-parented to the grandparent with a direct database update. No per-child hook fires.404 on every subpage's old URL, silently
Visit any of those dead URLsredirect_canonical() guesses: it matches the last path segment with LIKE 'team%' across every public post type and redirects to the first row it finds, in no particular order.Lottery sometimes the right page, sometimes an unrelated post whose slug starts the same way
Look at the hierarchy in wp-adminThe Pages list indents subpages only in the default unsorted, unfiltered view. The block editor shows a Parent dropdown and never shows subpages.Blind editors act without seeing what sits underneath

Core ticket #4328 has tracked this since 2007. Three plugins each cover one slice: Easy Hierarchy adds a tree view and a parent column, Completely Delete trashes and restores children with the parent, and Redirection Extended redirects children on a parent permalink change but only as an add-on to the Redirection plugin. None of them combines visibility, warnings before the damage, and a plan for the old URLs.

Hierarchy column, subtree filter and Tree view

On every supported post type the list gains a one-line Hierarchy column: the parent as a link, then the subpage count as a link that filters the list to that subtree. Trash dialog

Clicking Trash on a page with subpages, from a row action or a bulk action, opens a small modal instead of trashing immediately. One sentence states what will happen under the default policy. "Other options" reveals the two alternatives. URLs quoted here are expected ones; the outcome notice shows the actual URLs after slug conflicts are resolved. The chosen policy travels with the trash request. The block editor's own trash button already shows core's confirmation and cannot be extended, so there the default policy applies and the landing notice with Undo is the safety net.

After any action that changed URLs, the Pages list shows a one-paragraph notice with Undo and a "View redirects" link. In the editor the same message is a snackbar. Mechanism

How it works

Recording URL changes

Three hooks feed one recorder, and the recorder writes one entry per post whose own slug or parent changed. When children change parent together, through a trash or a permanent delete, it writes the old parent path once on the new parent, or in a small root list when the children become top level, so a thousand moved children still cost one write. A per-child entry is added only when a moved child's slug had to change to avoid a collision. The recorder never walks the subtree. The old path is built from the slug chain of the before-object with the permalink structure's placeholders left in, so drafts with empty slugs, the front page, and private pages all resolve the same way for every user. Recording happens only when the old URL was publicly reachable. Entries equal to the current path are pruned on write and again on read.

Trashing a parent

The policy is resolved and capabilities are checked before core acts. Inside the wp_trash_post action the plugin only snapshots current paths, because core has committed nothing yet and the trash can still fail. Mutation happens in trashed_post, after success. Re-parenting uses the same raw update and cache clear core uses in wp_delete_post(), so children's content is not re-filtered and their modified dates don't move. Up to the batch threshold everything runs inline; beyond it a background job processes batches with a progress notice, and Undo waits for it. Reversal is triggered by any transition out of trash, not only the Restore link, and restores subpages with their previous status.

Serving a redirect

Only runs when the built-in option is on, only for GET and HEAD, and at template_redirect priority 9 so it beats both redirect_canonical() and its fuzzy 404 guess. The requested path comes from the untouched query vars, pagename for pages or the post type's own variable for hierarchical custom types, normalized the way get_page_by_path() normalizes, with pagination, feed and embed suffixes set aside and re-applied to the target. The resolver tries the longest prefix first; on a hit it rebuilds a candidate from the matched post's current path plus the remainder, or from the remainder alone when the prefix is in the root list, and asks core to resolve it scoped to the post type. A candidate that still fails is fed back through the loop for chained changes, at most five rounds with a seen-set to break cycles. The final target must be publicly viewable. The URL passes wp_validate_redirect() after filtering, and the status code defaults to 301.

Persistence

Data model

Everything lives in core tables. Post meta is removed by core when a post is deleted, and uninstall.php removes the rest in batches of a thousand rows, per site on multisite. All plugin caches live in a hierarchy_guard cache group with its own last-changed key, bumped only by the plugin's own writes, because the posts key changes on every post or meta write anywhere on the site.

REST endpoint

One read-only route backs the editor panel, the classic meta box, the Tree view's lazy loading, and the redirects modal. It requires edit_post on the requested ID. Children are paged, counts are direct, and totals are capped. The same data is also exposed as a hierarchy_guard field on the REST page object so a DataViews column needs no extra request.

Code

Architecture

Namespaced PHP with Composer autoloading and no runtime Composer dependencies. One class per responsibility so each can be unit tested on its own. One PHP core serves two admin tracks: the classic list table that every supported version renders, and a DataViews track that registers the same field and trash action for the Site Editor's Pages list now and for the admin Pages screen when core moves it. JavaScript is built with @wordpress/scripts.

Filters for developers

  • hierarchy_guard_post_types: adjust the supported types.
  • hierarchy_guard_default_trash_policy: override the setting per post or per site.
  • hierarchy_guard_batch_threshold (default 200) and hierarchy_guard_count_cap (default 1,000).
  • hierarchy_guard_redirect_providers: add or remove detected redirect plugins and their CSV layouts.
  • hierarchy_guard_redirect_url and hierarchy_guard_redirect_status: change the target or the 301. The result still passes wp_validate_redirect().
  • hierarchy_guard_should_record: skip recording for a given post.
  • Action hierarchy_guard_children_reparented( $ids, $from, $to ) for integrations that need to react to the raw re-parent.

Proof

Testing

PHPUnit is the gate. Each scenario builds a small tree with the test factory, performs the action through the same functions wp-admin calls, and asserts on meta, on query counts where scale matters, and on the HTTP outcome.

  1. Rename a top-level page: exactly one ledger entry, on that page. A request for an old subpage URL resolves through the prefix match to the right subpage.
  2. Move a page under another parent: one entry on the moved page; old URLs of its subtree resolve.
  3. Chained changes: rename the parent, then move a child; old URLs from before both changes resolve within the round cap.
  4. Rename, then rename back: the entry is pruned; a stale entry equal to the current path is pruned on read.
  5. Serving on: 301 to the current permalink with pagination preserved; serving off: core's behaviour untouched; POST request: untouched; unknown path: core's guess runs.
  6. Trash with re-parent below the threshold: children's parent is the grandparent, modified dates unchanged, markers set, one entry on the grandparent plus one per child whose slug changed, summary stored.
  7. Trash with re-parent above the threshold: the first batch runs inline, a job is queued, the processor finishes it, Undo is disabled until done.
  8. Trash with the subtree policy: descendants trashed with the marker; untrash via Restore restores them with their previous status, not draft.
  9. Reversal fires on a REST status update out of trash, not only on wp_untrash_post().
  10. A trash that fails after wp_trash_post leaves children untouched and writes nothing.
  11. Capabilities: a user who can trash the parent but not edit a child gets "keep" for that child and a message saying so.
  12. Permanent delete: the deleted page's path is recorded on the grandparent, or in the root list for a top-level page, before core re-parents the children; old subpage URLs resolve.
  13. Draft ancestor with an empty slug, front page as parent, private page: paths computed from the slug chain match what core resolves.
  14. Hierarchical custom post type with a rewrite slug: entries include the prefix and resolve correctly.
  15. Plain permalinks: nothing is recorded and the server is inert.
  16. List table: the Hierarchy column adds at most two queries per screen regardless of row count; the subtree filter returns exactly the descendants and caps at 1,000.
  17. REST routes require edit_post; response shapes are stable; children page correctly.
  18. Markers are absent from a WXR export; old-path entries are present.

Manual checks on the Local site: with Redirection installed and without, confirm detection, deep links, CSV import into Redirection, and the three notice variants. Browser end-to-end tests for the trash dialog are a follow-up.

Sequence

Build order

Each step leaves the plugin activatable and tested. The riskiest logic comes first so the UI is built on something already proven.

  1. Scaffold the repo, wp-env, PHPCS, PHPUnit, and CI. Symlink into a Local site.
  2. Paths, Ledger, Resolver, and Change_Listener with their tests, including the query-count assertions. This alone makes every URL change observable and resolvable.
  3. Subtree queries with caps, and the cache group.
  4. Trash_Handler with capabilities, snapshot and apply, all three policies, reversal, and the Batch job and processor, with tests.
  5. Redirects: Providers detection, Server, CSV export, and the Settings › Writing section.
  6. REST routes, the page REST field, the editor panel, and the classic meta box.
  7. List table: Hierarchy column, subtree filter, parent dropdown, row action, trash Modal, Quick Edit inline warning, outcome notice and redirects Modal.
  8. Tree view with tree grid semantics, lazy loading, and server search.
  9. DataViews track: the hierarchy field and the replacement trash action, registered wherever the API is available.
  10. Notices, readme.txt, uninstall, translation pass, release zip.
Next step is a written implementation plan from this spec, then step 1. Open items: which Local site to symlink into, and whether the DataViews field and action registration APIs are public in the WordPress version current when step 9 begins.
Later or never

Out of scope for 1.0

  • One-click "Add to Redirection" and "Add to Safe Redirect Manager" adapters. Natural 1.1 candidates since both have stable PHP APIs; the CSV export in their layouts covers 1.0.
  • Incrementally maintained descendant counts stored on ancestors. Every such write would bump the posts cache key; the capped walk is enough.
  • A zero-query first-segment gate for the 404 handler. Cached misses with a TTL cover bot traffic; revisit if real sites show otherwise.
  • A redirect log screen. Declined; the outcome notice, the redirects modal, and the per-page panel cover auditing.
  • Attachment URLs under pages. Attachments have hierarchical URLs too, but they are not in the supported types and core's own attachment-page handling is changing.
  • Scanning post content for internal links that point at changed URLs. A different and much larger problem.
  • Non-hierarchical post types. Core already handles their old slugs.
  • Redirects after a permalink structure change. Affects every URL on the site, not the hierarchy.
  • Playwright end-to-end tests. Planned once the dialog settles.
