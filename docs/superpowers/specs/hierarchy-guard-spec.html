Hierarchy Guard

Shows the parent and child structure of pages inside wp-admin, warns before a slug change, re-parenting, or trash breaks a subtree, and makes sure every old URL has somewhere to go.

Why this exists

WordPress protects posts from broken URLs. It does nothing for pages.

Pages and every hierarchical custom post type build their URLs from the chain of ancestors. Change one link in that chain and every URL below it changes too. Core knows how to redirect an old slug for a post, but both halves of that mechanism explicitly skip hierarchical types. The behaviour below was verified by reading WordPress 6.8.1 source.

Editor actionWhat core doesWhat visitors get
Rename a page's slugNothing stored. wp_check_for_changed_slugs() returns early for hierarchical types, and wp_old_slug_redirect() returns early as well.404 on the page's old URL and on every subpage's old URL
Move a page under a different parentNothing stored, same two early returns.404 across the whole moved subtree
Trash a parentThe parent's slug is renamed to about__trashed on the spot. Subpages are left attached to it. No warning.404 on /about/team/ while the subpage stays live at /about__trashed/team/

Core ticket #4328 has tracked this since 2007. Three plugins each cover one slice: Easy Hierarchy adds a tree view and a parent column, Completely Delete trashes and restores children with the parent, and Redirection Extended redirects children on a parent permalink change but only as an add-on to the Redirection plugin. None of them combines visibility, warnings before the damage, and a plan for the old URLs.

Features and mockups

See

Visibility

Parent and child pages in the editor, a Hierarchy column and subtree filter in the list, and a Tree view of the same list.

Warn

Guard rails

A warning when the slug or parent changes on a page with subpages, and a one-sentence dialog before trashing a parent from the Pages list.

Recover

Safety net

Every URL change is recorded. The editor gets the exact redirects to add in their redirect plugin, or Hierarchy Guard serves them itself. Administrators can retarget or delete each one under Settings › Hierarchy Guard.

Mockups below use the default "Modern" admin colour scheme. The real plugin sets no colours: React surfaces come from @wordpress/components and PHP surfaces use core admin classes, so they follow whatever scheme and tokens the site has.

Editor sidebar panel

A "Hierarchy" document settings panel answers the two questions an editor has before changing anything: what is above this page, and what is underneath it. A plugin panel starts closed and renders nothing inside it, so nothing an editor must see lives only there. The warning appears under the page's Summary, right below the Parent row, the moment the slug or parent differs from the saved value on a published page with subpages. After a save that changed URLs, an editor notice says how many old URLs changed and offers View redirects for that change. The panel loads its data only when it is open or such an edit is made. Parent pages are listed when the page sits two or more levels deep, since the Summary already names the parent. Status is shown only when it isn't Published. The classic editor gets the same data as a read-only meta box, a plain confirmation when the form is submitted with a changed slug or parent, and, right after such a save made there, a notice at the top of the edit screen with a CSV download of the redirects that save needs. The panel and the box show where a page is now, not its past URLs: the redirects a change needs are offered when it happens.

Hierarchy column, subtree filter and Tree view

On every supported post type the list gains a one-line Hierarchy column: the parent as a link, then the subpage count as a link that filters the list to that subtree. The filter is also reachable from a "View subpages" row action. Its active state shows beside the heading the way core shows search results, as a breadcrumb, "Subpages of Company › About · Show all pages", where each ancestor links to its own subtree. There is no parent dropdown: a list of every parent page can't be bounded on a site with a million pages. The column costs one query per screen plus one to load the rows' parents, whatever the view; in core's indented tree mode the rows on screen are worked out from core's own query, and subpages the view hides, such as drafts under a published page, still count. Filtering carries a sort order so core renders normal paginated rows rather than its unsorted tree mode. "Tree" joins the views row next to All and Published; it shows the same table in hierarchical order with disclosure toggles, loads children on demand, and searches on the server.

Trash dialog

Clicking Trash on a page with subpages, from a row action or a bulk action, opens a small modal instead of trashing immediately. Its title is known at the click. One sentence states what will happen under the page's policy, naming what each number counts; until the subpages are checked it is built from the row. "Other options" reveals the two alternatives, with example URLs. URLs quoted here are expected ones; the redirects modal shows the actual URLs after slug conflicts are resolved. The chosen policy travels with the trash request only when the editor picks another option, and the server honours it only after core's own nonce checks again. The block editor's own trash button already shows core's confirmation and cannot be extended, so there the default policy applies and the landing notice with Undo is the safety net.

Outcome notice and redirects needed

After a trash, core's own notice on the Pages list says what happened to the subpages and keeps its Undo link. The URLs the trash changed get a notice of their own below it, styled by what handles them: a warning when nothing does. Trashing from the post editor lands on this Pages list, so the same notices cover it. A save that changed URLs gets the same sentence once, where it was made. A Quick Edit or block editor save gets it in place. A Bulk Edit gets it on the Pages list core redirects back to, below core's "pages updated" notice. A classic editor save gets it on the edit screen it lands on, and only there: a save made anywhere else never shows on a later classic visit. In the Site Editor's DataViews, which stay on screen, the message is a snackbar. The pairs live in a modal, computed on demand, cached for a few minutes and paged, where the provider-specific actions also live. The modal exists on the Pages list and in the block editor; on the classic editor's screen, and without JavaScript, the link is "Download redirects (CSV)" and downloads the CSV. The list notices are scoped to the post type's list screen, and the summary expires after thirty minutes or the next URL-changing action. A later change replaces the list an earlier notice offers, so a new notice on the Pages list takes the earlier ones' links, and an older list asked for says a later change replaced it. A trash's list is complete while its pages are in the Trash. Once a page a list has redirects for is deleted for good, the list is gone, and asking for it says a page they belong to was deleted for good: for a save, a page it moved or renamed; for a trash, a parent whose subpages moved up. A parent that moved nothing had nothing to list, so deleting it changes nothing.

Settings › Hierarchy Guard

Hierarchy Guard is not a redirect plugin. It is a minimal add-on for sites with no redirect plugin, or whose owners don't want to mix manual redirects with the ones this plugin generates. So its one admin page holds the three settings and the redirects the plugin recorded, and nothing else. It sits under Settings at options-general.php?page=hierarchy-guard, for users with manage_options, with core nav tabs: Settings | Redirects. The Settings tab holds the three fields, Post types, Trashing a page with subpages, and Redirects, the one switch for built-in redirects. They save the same hierarchy_guard_settings option through the Settings API. Nothing registers on Settings › Writing. Every link to the settings opens this page: the "Set up redirects" notice action, the panel's "Change this in Settings", and the readme. The plugin's row on the Plugins screen gets a "Settings" action link to it too.

Redirects tab

The Redirects tab is a core WP_List_Table of every redirect the plugin recorded, and only those. Each row is one ledger record: a page's _hierarchy_guard_path_{md5} entry, or one root-list entry, whose subpages became top level. Old URL is the recorded path, with "and the URLs under it" for a page target. Redirects to is the page's title, linked to its edit screen, with its current URL; for a URL target, the URL; for a root-list entry without an override, "Top level". Code is "Automatic", which is 302 while restoring a page from the Trash could undo the move and 301 otherwise, or the 301 or 302 chosen on Edit. Status is "Active", or says why the redirect isn't served, and a row shows the first reason that applies:

  • "Not active: a page uses this URL". A live page always wins; redirects act only on a 404.
  • "Not active: the page it points to isn't published".
  • "Not active: built-in redirects are off".

Search matches the old URL. A post type filter appears when more than one type is supported. Rows come 20 per page, sorted by old URL across the newest 1,000 records plus the root list; past that, a notice says so, the count reads "1,000+", and a search for a full old URL still finds any record. The newest records come from a capped list the ledger keeps per post type, so the post type filter shows that type's own newest records. Row actions are Edit and Delete, and Delete is also a bulk action. Delete asks first, from a row, the Edit view or in bulk, with a browser confirmation as core asks before deleting a term: "Delete the redirect from /about/team/? This can’t be undone.", or once for a bulk selection, "Delete the selected redirects? This can’t be undone." Without JavaScript it deletes directly, as core does. There is no Add button: adding redirects by hand is a redirect plugin's job. When built-in redirects are off, a notice above the table says "Built-in redirects are off, so these redirects aren't served. Turn them on in the Settings tab." When a redirect plugin is detected, a notice names it and says these are the redirects Hierarchy Guard recorded, which its notices after each change offer to add there.

Editing a redirect

Edit is its own view of the page, &action=edit&redirect=<id>, behind a nonce. Old URL is read only. One "Redirect to" field takes a URL, or a path on this site such as /company/about/, which is read against the home URL; it is a plain text field, so a path isn't stopped by the browser, and its help says so. If it resolves to a supported page on this site through url_to_postid(), it is saved as a page target, which follows that page when it moves and covers the URLs under the old one. Any other http(s) URL is saved as a URL target, which redirects only that exact old URL: the URLs under it stop redirecting through this record, and the form says so before saving. A page of another post type counts as any other URL, because a record belongs to its own post type. There is no page picker, because a list of every page can't be bounded on a large site, and the form works without JavaScript. For a root-list entry whose subpages are top level and that has no URL target, the view says "Now redirects to the same page at the top level, for example /about/team/ to /team/.", and the field starts empty, with the help "Leave empty to keep this. Enter a URL to send these URLs somewhere else."; saving it empty keeps the entry and saves only the code. Code is Automatic, 301 or 302. Save and Cancel sit under the form, with a Delete link. Saving returns to the Redirects tab with a core notice confirming it. Deleting, from this view, a row or in bulk, says the old URL no longer redirects through this record; a shorter recorded URL, or core's own guess, may still send it somewhere.

Mechanism

How it works

Recording URL changes

Three hooks feed one recorder, and the recorder writes one entry per post whose own slug or parent changed. When children change parent together, through a trash or a permanent delete, it writes the old parent path once on the new parent, or in a small root list when the children become top level, so a thousand moved children still cost one write. A per-child entry is added only when a moved child's slug had to change to avoid a collision. The recorder never walks the subtree. The old path is built from the slug chain of the before-object with the permalink structure's placeholders left in, so drafts with empty slugs, the front page, and private pages all resolve the same way for every user. Recording happens only when the old URL was publicly reachable. Entries equal to the current path are pruned on write and again on read. A page published at a path, or a published page moved or renamed onto one, takes that path: other live posts' entries for it and its root-list entry are dropped, with one seek on the hashed key and a read of the root-list option, so the URL belongs to the page that has it now, and if that page moves on it records the path itself. A post in the trash keeps its entry. The earlier page's subpage URLs under that path go with it: re-create a page at a moved or trashed parent's path, and the old URLs of that parent's subpages under it no longer redirect: each is a 404 unless the new page has a subpage of its own there. Under the trash-the-subpages policy, a subpage trashed with its parent that is deleted for good records each of its own subpages' URL from before the trash on that subpage, for a subpage that was published then: one in the trash by the status wp_trash_post() kept for it, as the Trash screens trash; a subpage trashed by a status change keeps no such status and gets nothing, never on the deleted page's parent or in the root list, so a subpage that outlives it keeps its old URL.

Trashing a parent

The policy is resolved and capabilities are checked before core acts. Inside the wp_trash_post action the plugin only snapshots current paths, because core has committed nothing yet and the trash can still fail. Mutation happens in trashed_post, after success. Re-parenting uses the same raw update and cache clear core uses in wp_delete_post(), so children's content is not re-filtered and their modified dates don't move. Up to the batch threshold everything runs inline; beyond it the first batch runs inline and a background job processes the rest with a progress notice. Raw moves and core trash or restore calls have separate budgets, because a core call costs far more, and each background run is time-boxed. One job and one lock exist per root, so a trash job and a restore for the same page never run at once. An hourly watchdog restarts a stalled job and gives up after seven days. In a Pages-list bulk action, pages core itself is about to trash or restore are left to core, so its loop never meets a page the plugin already handled. The restore runs after the page's own save has finished, not inside it, and a page that is merely in the trash is never redirected to its parent, so no browser caches that redirect. An entry on a page above it in its parent chain never redirects that URL, however that page was renamed or moved since, even when that page held the URL itself in between. A newer page outside that chain that had the URL since and moved on still gets it, as a 302 while the page in the trash could take it back. The trash-the-subpages policy falls back to moving them up when a subtree has more than 1,000 pages, so one click never fills the trash beyond what core can empty. Until the Pages-list notice arrives, core's own "moved to the Trash" message gains one sentence saying what happened to the subpages. Reversal is triggered by any transition out of trash, not only the Restore link, and restores subpages with their previous status. Capability checks use the user who trashed the parent. When there is no user, as in cron or WP-CLI without --user, the call is trusted the way core trusts its own API. Each page's policy is filterable, which is how the Pages list dialog passes the editor's choice. If a subpage's slug is already taken under its new parent, it gets a numbered slug and its old URL is recorded on it directly. Restoring gives it back its original slug when that is free again. A batch still running when its parent is restored stops, and the restore takes back what it had done. Restoring also records each moved-back subpage's interim URL, so links made while the parent was in the trash keep working.

Editing a recorded redirect

No new post type and no table: an edit lives next to the record it changes. Retargeting a record to another page moves it: the path is recorded on that page and forgotten on the old holder, or moved out of the root list. A URL target or a chosen code is a sibling post meta on the holder, _hierarchy_guard_target_{md5}, with the same hash as the entry, holding { url, code }. A root-list entry's override lives in a second non-autoloaded option, hierarchy_guard_root_targets, keyed by post type then path. Deleting a record deletes its override with it. Every edit bumps the ledger's cache key, so the resolver and the cached redirect lists see it on the next request. The page and every action on it check manage_options and a nonce, so only administrators can point a redirect off the site, and only at an http(s) URL.

Serving a redirect

Only runs when the built-in option is on, only for GET and HEAD, and at template_redirect priority 9 so it beats both redirect_canonical() and its fuzzy 404 guess. The requested path comes from $wp->request with the index.php root removed. Query vars can't be used: with the default /%postname%/ structure, core skips every page rule whose path matches no page, so a 404 for an old page path carries no pagename at all, or an unrelated attachment value for two-segment paths. Pagination, comment-page, trackback, feed and embed suffixes are set aside and re-applied to the target, and the path is normalized the way get_page_by_path() normalizes. A path under a hierarchical custom type's rewrite prefix is tried as that type first, then as a page. The resolver tries the longest prefix first; on a hit it rebuilds a candidate from the matched post's current path plus the remainder, or from the remainder alone when the prefix is in the root list, and asks core to resolve it scoped to the post type. A record with a URL target answers only its exact old path, with that URL; for a longer path, matching continues as if that record weren't there, so a shorter prefix can still answer. A root-list entry's override is read from hierarchy_guard_root_targets the same way. A candidate that still fails is fed back through the loop for chained changes, at most five rounds with a seen-set to break cycles. A page target must be publicly viewable, and its URL passes wp_validate_redirect() after filtering. A URL target, which may be on another host, is sent with wp_redirect() after esc_url_raw(), http(s) only. The status code defaults to 301, or 302 while a restore from the trash could still undo the move the redirect follows, so no browser keeps a redirect that a restore would make wrong. A chosen code replaces the automatic one. A live page at the old URL always wins, because the server acts only on a 404. The batch resolver that builds a change's redirect lists honours the same overrides, so the modal and the CSV list what the server sends.

Persistence

Data model

Everything lives in core tables. Post meta is removed by core when a post is deleted, and uninstall.php removes the rest in batches of a thousand rows, per site on multisite. All plugin caches live in a hierarchy_guard cache group with its own last-changed key, bumped only by the plugin's own writes, because the posts key changes on every post or meta write anywhere on the site. Edits and deletes on the Redirects tab are plugin writes and bump it too.

REST endpoint

One read-only route backs the editor panel, the classic meta box, the Tree view's lazy loading, and the redirects modal. It requires edit_post on the requested ID. Children are paged, counts are direct, totals are capped, and the title of a post the user may not read stays private. The same data will also be exposed as a hierarchy_guard field on the REST page object, so a DataViews column needs no extra request.

Code

Architecture

Namespaced PHP with Composer autoloading and no runtime Composer dependencies. One class per responsibility so each can be unit tested on its own. One PHP core serves two admin tracks: the classic list table that every supported version renders, and a DataViews track that registers the same field and trash action for the Site Editor's Pages list now and for the admin Pages screen when core moves it. JavaScript is built with @wordpress/scripts.

Filters for developers

  • hierarchy_guard_post_types: adjust the supported types.
  • hierarchy_guard_default_trash_policy: override the setting site-wide.
  • hierarchy_guard_trash_policy( $policy, $post ): choose the policy for one page; the Pages list dialog uses it.
  • hierarchy_guard_batch_threshold (default 200 raw moves per step), hierarchy_guard_core_call_threshold (default 25 core trash or restore calls per step) and hierarchy_guard_count_cap (default 1,000).
  • hierarchy_guard_redirect_providers: add or remove detected redirect plugins and their CSV layouts.
  • hierarchy_guard_redirect_url and hierarchy_guard_redirect_status: change the target or the code, including a chosen one. A page target's result still passes wp_validate_redirect(); a URL target's is sent only while it is http(s).
  • hierarchy_guard_should_record: skip recording for a given post.
  • Action hierarchy_guard_children_reparented( $ids, $from, $to ) for integrations that need to react to the raw re-parent.
  • Action hierarchy_guard_job_finished( $job ) when a background batch job completes.

Proof

Testing

PHPUnit is the gate. Each scenario builds a small tree with the test factory, performs the action through the same functions wp-admin calls, and asserts on meta, on query counts where scale matters, and on the HTTP outcome.

  1. Rename a top-level page: exactly one ledger entry, on that page. A request for an old subpage URL resolves through the prefix match to the right subpage.
  2. Move a page under another parent: one entry on the moved page; old URLs of its subtree resolve.
  3. Chained changes: rename the parent, then move a child; old URLs from before both changes resolve within the round cap.
  4. Rename, then rename back: the entry is pruned; a stale entry equal to the current path is pruned on read.
  5. Serving on: 301 to the current permalink with pagination preserved; serving off: core's behaviour untouched; POST request: untouched; unknown path: core's guess runs.
  6. Trash with re-parent below the threshold: children's parent is the grandparent, modified dates unchanged, markers set, one entry on the grandparent plus one per child whose slug changed, summary stored.
  7. Trash with re-parent above the threshold: the first batch runs inline, a job is queued, the processor finishes it; restoring mid-job stops the job and brings back what moved.
  8. Trash with the subtree policy: descendants trashed with the marker; untrash via Restore restores them with their previous status, not draft.
  9. Reversal fires on a REST status update out of trash, not only on wp_untrash_post().
  10. A trash that fails after wp_trash_post leaves children untouched and writes nothing.
  11. Capabilities: a user who can trash the parent but not edit a child gets "keep" for that child and a message saying so.
  12. Permanent delete: the deleted page's path is recorded on the grandparent, or in the root list for a top-level page, before core re-parents the children; old subpage URLs resolve.
  13. Draft ancestor with an empty slug, front page as parent, private page: paths computed from the slug chain match what core resolves.
  14. Hierarchical custom post type with a rewrite slug: entries include the prefix and resolve correctly.
  15. Plain permalinks: nothing is recorded and the server is inert.
  16. List table: the Hierarchy column adds at most two queries per screen regardless of row count, in core's tree mode too, and counts subpages the current view hides; the subtree filter returns exactly the descendants and caps at 1,000; no child query sorts every child of a parent.
  17. Redirect pairs of a change: computed from the pages that change moved or renamed, at their URLs from just before it; published pages only, depth first in menu order, capped; none without pretty permalinks; every pair listed is one the built-in server serves (an old URL a live page uses now is never listed), and its CSV row says the 301 or 302 a request for it gets; a trash's list is complete while its pages are in the Trash; a list is gone once a page it has redirects for is deleted for good (a save's page, or a trashed parent whose subpages moved up), and a deleted parent that moved nothing leaves it as it was; the blocks of a bulk trash cost the same few queries whatever its size.
  18. Where a change shows: a classic save's notice prints once on the edit screen it lands on, and a Quick Edit, block editor or Bulk Edit save never prints on a later classic visit; a Bulk Edit's notice prints once on the Pages list core returns to; a Bulk Edit of a parent and its subpage, in either order, lists each page at its URL from before the request; a request of many roots writes its change once.
  19. REST routes require edit_post; response shapes are stable; children page correctly.
  20. Markers are absent from a WXR export; old-path entries are present.
  21. Redirects tab sources: one row per _hierarchy_guard_path_{md5} entry and one per root-list entry, each with its override; a root-list entry without an override reads "Top level"; nothing else the plugin stores becomes a row.
  22. Redirects tab search and paging: search matches the old URL; the post type filter appears only when more than one type is supported; 20 rows per page, sorted by old URL with root-list entries in the same order, over the newest 1,000 records, with the notice past that and a full-URL search reaching any record.
  23. Edit to a page: the record moves onto that page, or out of the root list, follows the page when it moves, and covers the URLs under the old one. Edit to a URL: only the exact old URL redirects there, and a longer path resolves as if the record weren't there. Each code: Automatic gives 301, or 302 while a restore could undo the move; a chosen 301 or 302 is sent as chosen. Delete removes the record and its override, and the old URL is a 404. Every edit and delete bumps the ledger cache key. A path on this site is read against the home URL; a top-level root-list entry saved with the field empty stays top level with its code saved. Delete asks first with JavaScript, and deletes directly without it.
  24. Capability and nonce checks: without manage_options the page, the Edit view, save, delete and bulk delete are refused; without a valid nonce nothing is saved or deleted; a URL that isn't http(s) is not saved.
  25. Status labels: Active; "a page uses this URL" when a live page answers it; "the page it points to isn't published" for a draft, private or trashed target; "built-in redirects are off" when serving is off; each row shows the first that applies.
  26. Resolver and batch parity with overrides: for page targets, URL targets and chosen codes, the pairs a change lists and its CSV codes match what the server sends; a URL target goes out through wp_redirect(); a live page at the old URL always wins.
  27. Settings links: "Set up redirects", the panel's "Change this in Settings", the Plugins row's "Settings" link and the readme point to options-general.php?page=hierarchy-guard; nothing registers on Settings › Writing.

Manual checks on the Local site: with Redirection installed and without, confirm detection, deep links, CSV import into Redirection, the three notice variants, and both Redirects tab notices. Browser end-to-end tests for the trash dialog are a follow-up.

Sequence

Build order

Each step leaves the plugin activatable and tested. The riskiest logic comes first so the UI is built on something already proven. Plans 1 to 3 cover steps 1 to 7. Plan 4 is step 8, plan 5 is step 9, and plan 6 is steps 10 and 11.

  1. Scaffold the repo, wp-env, PHPCS, PHPUnit, and CI. Symlink into a Local site.
  2. Paths, Ledger, Resolver, and Change_Listener with their tests, including the query-count assertions. This alone makes every URL change observable and resolvable.
  3. Subtree queries with caps, and the cache group.
  4. Trash_Handler with capabilities, snapshot and apply, all three policies, reversal, and the Batch job and processor, with tests.
  5. Redirects: Providers detection, Server, CSV export, and the settings option.
  6. REST routes, the page REST field, the editor panel, and the classic meta box.
  7. List table: Hierarchy column, subtree filter with its breadcrumb, row action, trash Modal, Quick Edit inline warning, outcome notices and redirects Modal.
  8. Settings › Hierarchy Guard: the Settings tab, the Plugins row link and every settings link pointed at the page, the Redirects tab, the Edit view, overrides in the ledger, and the resolver and batch resolver honouring them.
  9. Tree view with tree grid semantics, lazy loading, and server search.
  10. DataViews track: the hierarchy field and the replacement trash action, registered wherever the API is available.
  11. Notices, readme.txt, uninstall, translation pass, release zip.
Next step is plan 4's written implementation plan from this spec. Open item: whether the DataViews field and action registration APIs are public in the WordPress version current when plan 6 begins.
Later or never

Out of scope for 1.0

  • Lists of a page's past URLs in the editor panel or the meta box. Declined: the redirects a change needs are offered when it happens, the Redirects tab lists every recorded old URL, and the built-in server keeps them working.
  • Listing redirects for pages deleted for good in a change's notice, modal or CSV. The built-in redirects still serve their old URLs, and the Redirects tab lists them.
  • Listing, in a trash's redirect list, the subpages of a subpage it moved that another user then trashed. The second trash moves them up, and the first trash's notice, modal and CSV leave them out; the built-in redirects still serve their old URLs.
  • One-click "Add to Redirection" and "Add to Safe Redirect Manager" adapters. Natural 1.1 candidates since both have stable PHP APIs; the CSV export in their layouts covers 1.0.
  • Incrementally maintained descendant counts stored on ancestors. Every such write would bump the posts cache key; the capped walk is enough.
  • A zero-query first-segment gate for the 404 handler. Cached misses with a TTL cover bot traffic; revisit if real sites show otherwise.
  • Adding redirects by hand. Hierarchy Guard is not a redirect plugin: the Redirects tab manages only what it recorded, and a site that needs its own redirects is better served by a redirect plugin.
  • Import and export of redirects. The CSV a change offers, in the detected plugin's layout, is the one way out.
  • Regex or wildcard redirects. A page target already covers the URLs under its old path.
  • Hit counts and logs. The Redirects tab shows what the plugin recorded and whether each is served, not who followed it.
  • Attachment URLs under pages. Attachments have hierarchical URLs too, but they are not in the supported types and core's own attachment-page handling is changing.
  • Scanning post content for internal links that point at changed URLs. A different and much larger problem.
  • Non-hierarchical post types. Core already handles their old slugs.
  • Redirects after a permalink structure change. Affects every URL on the site, not the hierarchy.
  • Playwright end-to-end tests. Planned once the dialog settles.
